# web-demo/ — the hosted live prototype, not the graded deliverable

`dock/` stays the graded submission: a stdlib Python CLI, no UI, no network
calls, no LLM. It has nothing to put behind a URL. This directory exists
only because the submission form asks for a "Live Prototype / Demo URL" —
see `docs/SUBMISSION.md`.

Live at: **https://evermon-demo.nazrijz336.workers.dev**

## What this actually is

A Cloudflare Worker serving a static single-page app (`public/`) — no
server-side code, everything runs in the visitor's browser. It has two
parts, and they are not the same thing:

1. **Browsing the real dataset.** `public/data/emails.json` is exported
   once, at build time, by `scripts/export_dataset.py` — which calls
   `dock.pipeline.decide()` and `dock.documents.render()` directly. Every
   category, comparison outcome, and field value shown for the 520 real
   emails is what the actual graded Python pipeline produced. Nothing here
   re-runs classification or document parsing; the browser only displays
   what Python already decided.

2. **The "test it yourself" playground**, which *does* run logic live, in
   the browser: `src/lib/compare.ts` is a hand-ported copy of
   `dock/fields.py`'s value-comparison half (locode stripping, weight
   normalisation, container parsing, blank detection) — **not** the
   label-alignment half. It doesn't decide whether "Load Port" means the
   same thing as "Port of Loading"; that alignment already happened in
   Python, at export time. What runs client-side is only "do these two
   *already-aligned* field values mean the same thing" — so a visitor can
   edit `NHAVA SHEVA, INDIA (INNSA)` down to `NHAVA SHEVA, INDIA` and watch
   it still match, live.

Porting the diff logic risks it drifting from the Python original, so it's
checked, not assumed: `scripts/verify_parity.ts` runs the TypeScript
`compare()` over all 109 real emails that have both an SI and a BL parsed
(the other 91 `BL_COMPARISON` emails are the "please send the draft BL"
handover requests — nothing to compare yet, by design; see the root
`README.md`) and diffs the result against Python's own answer for every
one. `npm run verify-parity` — 0 drift, checked before this was deployed.

## Running it

```bash
cd web-demo
npm install
npm run export-data     # regenerate public/data/emails.json from the real bundle (needs Python + dock/)
npm run verify-parity    # TS compare() vs the Python original, all 109 real comparisons
npm run dev               # wrangler dev, local
npm run deploy            # builds src/app.ts with esbuild, then wrangler deploy
```

`public/app.js` is build output (esbuild-bundled from `src/app.ts`), not
source — regenerated by `npm run build`/`deploy`, gitignored.

## What is real and what is not

**Real:** the 520-email dataset shown, every category/status/field value
(computed by the actual `dock/` pipeline, not this page); the comparison
rules in the playground (parity-verified against Python, not reimplemented
independently); the "escalates with a reason" behaviour (the same four
`NEEDS_REVIEW` reasons `dock/review.py` defines).

**Not real, and not pretended to be:** this is not a live inbox — there is
no server, no incoming email, nothing to point a real mailbox at. The
"flying email" animation is a fixed visual sequence over precomputed data,
not a live processing pipeline running per request. The playground's field
comparison is real logic, but it is not full document parsing — paste a
whole PDF/DOCX/XLSX and nothing happens; it only accepts already-extracted
field values, same as the input `dock/compare.py` itself expects.
